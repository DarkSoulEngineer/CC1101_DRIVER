# Project instructions

## Context and invariants
- ESP32-S3 firmware using ESP-IDF v6.1. Native driver: `components/cc1101`; shared-bus bring-up: `components/hw_init`; RFuzz application: `components/rfuzz` (radio A/B TX and RX, profile coordination, console, and main loop in one component); `main/` is the entrypoint only. Use normal header interfaces and independent CMake compilation of `.c` modules, never textual `.c` includes.
- Two CC1101 radios share SPI3 with manual chip selects: A CS GPIO9 / GDO0 GPIO4, B CS GPIO10 / GDO0 GPIO5; shared MISO13, MOSI11, SCK12. GDO2 is not wired.
- Serialize shared-bus access with the existing bus mutex and preserve its ownership contract. Do not introduce nested locking, competing register writers, or mode changes during another owner's transaction. The main application owns mode transitions; a single console reader submits commands, rather than multiple consumers racing for UART input.
- ISR work must be bounded: no SPI, logging, or allocation. Defer processing to task context; use bounded capture storage and report drops instead of promising lossless data.
- Preserve the baseline: 433.92 MHz OOK, requested 38400 baud (approximately 38.383 kbps with register quantization), four-byte `DE AD BE EF` payload with hardware CRC, and `CC1101_DEFAULT_PA_433_MHZ=0xC8`, OOK PATABLE `{0x00, 0xC8}`, PA index 1: nominal +7 dBm conducted, not a measured power or RF compliance guarantee. The current lean firmware does not transmit automatically, so the historical ~5 s automatic-test cadence is not active; do not silently increase TX power, repetition rate, or airtime.

## Application module boundaries
The earlier module split passed ESP-IDF build and host regression checks; that is not evidence for later profile/RMT changes or hardware operation. Keep the single main-loop owner, without a new framework or tasks. Every RFuzz module is its own ESP-IDF component under `components/`, with public headers in `include/` and sources in `src/`; `main/` holds only the entrypoint.
- `main/main.c`: thin `app_main` entrypoint that calls `rfuzz_run()` (provided by `components/rfuzz`); no policy or radio code.
- `components/rfuzz`: the RFuzz application. It is a top-level component depending on `cc1101`, `hw_init`, and three nested sub-components registered through `EXTRA_COMPONENT_DIRS`: `components/rfuzz/components/terminal` (UART console, `terminal.h`), `components/rfuzz/components/profile` (coordinated modulation, `profile.h`), and `components/rfuzz/components/radio` (Radio A/B TX and RX, `radio.h`/`tx.h`/`rx.h`). The top-level component compiles only `src/rfuzz.c` (the main loop, entry `rfuzz_run()`). Radio A TX send/idle, Radio B packet/raw reception plus listen-only reporting, coordinated A/B profile transitions, the bounded UART parser, and the main loop all live here. Do not reach into private radio handles or state from outside; use the public headers listed above. Stop B capture before taking the bus mutex once; use private-handle `*_locked` wrappers (which never lock) to apply A packet, apply B selected format, start/arm B, and snapshot both before publishing validity. On partial failure, stop capture, best-effort IDLE both under the owned lock, invalidate; do not claim rollback. No automatic TX or golden-payload validation; Radio A stays idle.
- Register each `.c` implementation in its component's `CMakeLists.txt` and declare direct dependencies through `REQUIRES`; include headers only and avoid cross-module access to private state.

## Current implementation goal (not a completion claim)
Radio B selection is packet (default) versus raw digital demodulator output on GDO0 GPIO5 for the selected modulation, not just OOK. Commands are `help`, `status`, `rx packet`/`mode pck` (also `mode packet`), `rx raw`/`mode raw`, `mod ook`, `mod ask`, `mod 2fsk` (`mod fsk` alias), and `mod gfsk`, newline-terminated over UART0 at 115200 baud. The bounded ASCII parser is case-insensitive, allows whitespace, rejects extra arguments, and has no radio effects. There is no automatic transmission and no golden-payload validation: Radio A is configured but stays idle, and Radio B reports whatever it receives (arbitrary compatible payloads and CRC, no golden comparison). Mode-only changes affect B, preserve modulation, and defer until a pending coordinated profile transition completes. Each accepted modulation request coalesces to the latest request; failure requires an explicit modulation command to recover. Repeated modulation commands reapply safely. Raw mode is not IQ/analog sampling, lossless capture, or automatically decoded bits.

Raw capture uses RMT exclusively instead of B's packet GPIO IRQ: 1 us ticks/filter, 5 ms idle termination, 1024-symbol partial blocks, two delivery slots (~12 KiB static capture storage including the receive buffer). Service/rearm before formatting, borrow at most one block and release it, drain at most two per background call, emit at most one serial batch/sec with at most 16 pulse previews. Skip zero durations; never synthesize first-edge timestamps or continuous streams from callback notification times. Preserve epoch/sequence/is-last metadata; partial/final framing is not a packet boundary. Keep cumulative output-suppressed blocks/pulses separate from callback/event drops, known dropped symbols, rearm/gap counts, and unknown hardware loss. RMT ISR work is bounded copies/accounting only: no SPI, logging, allocation, task-context teardown, or register changes. Stop invalidates preparation, so always prepare before arm. Restore packet IRQ behavior on return.

Candidate profiles retain 433.92 MHz, ~38.383 kbps, 101.5625 kHz BW and C8 ceiling. OOK PA is `00/C8`; ASK is true two nonzero levels `34/C8` (nominal -10/+7 dBm, ~17 dB contrast). 2-FSK/GFSK use `DEVIATN=35` (~+/-20.63 kHz). These are hardware-unvalidated candidates, not arbitrary valid parameter combinations or a compliance guarantee.

## Staged roadmap — future items are NOT implemented by this goal
1. **Current scope:** coordinated four-profile modulation selection, packet/raw mode, and bounded RMT digital capture. Radio A is configured but stays idle (no automatic TX); B reports received packets without golden comparison. Validate these changes separately before deployment.
2. **Future validated serial profiles:** tune/measure candidate profiles, then add coordinated rate / RX bandwidth / deviation controls. Reject arbitrary invalid combinations; distinguish requested settings from quantized register values and actual readbacks.
3. **Future packet controls:** sync word and detection, preamble length, CRC, whitening, and address filtering, with validated profile transitions and compatible framing on both radios.
4. **Future signal / TX choices:** explicit signal types and TX waveform choices, plus a manual transmit command if needed (the lean build has no automatic TX). Further RF-changing work needs separate approval.
5. **Future capture and verification:** measured RMT timing/overflow/backpressure limits, repeated multi-profile packet/raw transitions, and approved hardware tests. Improve reliability without implying lossless capture.

## Verification and permission boundaries
- Use read-only source inspection and `git diff --check` for documentation changes. For implementation work, run only the checks assigned by the task owner; ESP-IDF v6.1 `idf.py build` is the normal build command when requested and its environment is available. Do not claim builds or hardware results that were not observed.
- Require explicit consent before flashing, starting RF transmissions beyond the existing runtime, committing/pushing, or making system/toolchain changes. Do not launch a serial monitor casually: reset/boot may resume the existing transmitter. Machine-specific ports (often CH343 on COM14 here) must be confirmed rather than hard-coded.
- Keep README RF/legal source caveats intact. A historical packet-link test does not validate a new selector, raw capture, radiated power, or regulatory compliance.
- Evidence is version-specific: the selector at `f06cca6` was hardware-tested; subsequent module reorganization passed build/host tests but was not flashed. New coordinated-profile/main/RX host mock suites and the final ESP-IDF v6.1 whole build (including corrected RMT teardown) passed; `ninja -j1` succeeded after the initial parallel build hit an unrelated LCD compiler crash. The RFuzz application now lives in a single `components/rfuzz` component depending on `cc1101` and `hw_init`; it was built with ESP-IDF v6.1 in this lean configuration and was not flashed. Profiles/RMT remain unflashed and have no hardware validation. Do not transfer earlier hardware validation to these changes.
